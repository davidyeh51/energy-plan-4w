# 四週精力維持計畫 · 執行台

把一份 Markdown 計畫書變成會自己算數的執行工具：每日 30 秒打卡 → 自動推導熱量缺口、瘦體重護欄、依從度與四週趨勢。

**線上版**：https://davidyeh51.github.io/energy-plan-4w/

---

## 這個網站做了什麼

| | |
|---|---|
| **儀表板** | 本週唯一要新增的決策、四週節奏、三個核心指標（瘦體重 > 腰圍 > 體重）、本週能量缺口進度、四張趨勢圖 |
| **今日打卡** | 先選「平日 / 應酬日」，介面隨之切換成對應的規則清單。體重、步數、入睡、精力 4 個欄位 + 勾選項 |
| **每週量測** | 週日晨起體脂與腰圍，含四項固定條件檢核；自動換算瘦體重並與護欄比對 |
| **計畫全文** | 原文的完整論述，但所有數字改為依你的基線即時計算 |
| **訓練課表** | W1–W2 降階版 / W3–W4 進階版，含 8 次訓練的完成紀錄 |
| **設定 · 同步** | 身體基線、推導參數總表、雲端同步、CSV / JSON 匯出 |

## 設計上的三個決定

**1. 個人數字不寫在原始碼裡。** 這個 repo 是公開的。身高、體重、體脂率、出生年月全部由使用者在「設定」頁輸入，存在瀏覽器的 `localStorage` 與使用者自己的同步空間。原始碼裡只有計算邏輯。

**2. 缺口用「依從度」估算，不要求記錄熱量。** 原計畫明講「記份量，不用計算」。所以每天不是輸入 kcal，而是勾選當天做到哪幾條規則；每條規則帶一個熱量權重，達成比例乘上該日的目標缺口，再加上步數超出基線的額外消耗。這是估算值，用途是看趨勢與依從度，不是精算熱量。

**3. 介面照「一次只改一個決策點」的節奏走。** 本週尚未啟動的規則會變灰並標示啟動週次——做了算加分，但不列入本週的依從度分母。W1 完全不設缺口目標，因為它的任務是建立基線。

## 與原始 v1.0 文件的兩處修正

- **走路增量的熱量被高估。** 原文寫「+3,000 步 ≈ 250–300 kcal」。步行實際約 0.5 kcal/kg/km，3,000 步約 2.2–2.4 km，換算下來大約是原文的一半。本站按體重逐人實算。
- **飲食缺口反而被低估。** 原文的「飲食缺口 2,300 kcal/週」低於它自己列出的雙預算制實際值。兩處誤差方向相反、大致抵消，最終週缺口與原文的 3,300 kcal 幾乎一致，預期速率仍是每月 1.4–1.8 kg。結論不變，過程數字改成可驗算的。

另外把紅旗門檻「一個月 > 4.3 kg」改成「一個月超過體重的 5%」，讓它與基線脫鉤。

## 雲端同步（選用）

不設定也能用——資料存在瀏覽器 `localStorage`。要跨手機／電腦共用時：

1. 在 Supabase 專案的 SQL Editor 執行一次 [`supabase-setup.sql`](supabase-setup.sql)
2. 把同步碼貼進網站「設定 · 同步」頁，按「啟用同步」

### 安全設計

`ep_state` 表開啟 RLS 且**不建立任何 policy**，anon 金鑰無法直接讀寫。唯一出入口是兩個 `SECURITY DEFINER` 函式 `ep_pull` / `ep_push`，兩者都要求提供 32 位十六進位的 `space_key`。所以：

- 連線金鑰**不放在這個 repo 裡**，只存在使用者自己的瀏覽器
- 就算金鑰外流，沒有 `space_key` 也讀不到任何資料

多裝置的合併規則是逐日 last-write-wins（比對每筆紀錄的 `ts`），不是整份覆蓋，所以手機與電腦分別打卡不會互相蓋掉。

## 匯出

「設定 · 同步」頁可匯出：

- **每日 CSV** — 每天一列，含所有勾選項、估計缺口、依從度
- **每週 CSV** — 每週一列，含 7 日均重、體脂、瘦體重、護欄、平均步數／入睡／精力
- **完整 JSON 備份** — 可再匯入合併

CSV 為 UTF-8 BOM，Excel 與 Google Sheet 直接開啟不會亂碼。

## 技術

單一 `index.html`，無建置流程、無框架、無外部請求。圖表是手繪 inline SVG，字體用系統中文字族。支援深／淺色與行動裝置。
